## Google 503 diagnosis and environment verification

Local effective Settings and ignored frontend configuration were checked using
presence flags and equality comparisons only. No credentials, tokens, API keys or
private file contents were printed or saved.

- Backend project ID is `brandsentry-68d05`; frontend project matches, and frontend
  auth domain matches that project's firebaseapp.com domain. All four frontend
  Firebase config fields and API base are present. This confirms configuration
  consistency, not Google Console provider/domain permissions.
- FIREBASE_SERVICE_ACCOUNT_JSON, FIREBASE_SERVICE_ACCOUNT_FILE and
  GOOGLE_APPLICATION_CREDENTIALS are absent. FIREBASE_AUTH_EMULATOR_HOST is absent.
- Both localhost and 127.0.0.1 development origins are allow-listed. Effective local
  cookies use Secure=false and SameSite=lax, as expected for development.
- Installed `firebase-admin==6.9.0` successfully initializes its default app with
  explicit projectId, but `_auth_client.Client.__init__` calls
  `app.credential.get_credential()` before token verification. Its default
  ApplicationDefault credential calls google.auth.default().
- The actual local verifier reproduces
  `FirebaseNotConfiguredError -> DefaultCredentialsError`, before ID-token checks
  or certificate download. This explains the reported local 503; it is not
  evidence of a bad genuine Google token. The diagnostic used deliberately invalid
  input, never a user's ID token.

**Answer:** a private service-account JSON file is not strictly required if valid
ADC is provided by another supported identity source (e.g. workload identity).
But credential-free, project-ID-only verification does **not** work through this
implementation's Admin SDK auth client. Passing initialize_app is insufficient.
No unsigned-token fallback, anonymous credential workaround, emulator mode or
relaxed signature/expiry/audience/issuer checking was introduced.

Next action: provision server-only credentials/ADC for the intended project, then
restart the backend and repeat genuine Google browser sign-in. Configuring private
JSON inline is already supported and does not require a JSON file on disk. Remote
Railway configuration was not inspected or changed. Genuine Google success,
certificate-fetch availability, Google Console authorised domains/provider state
and deployed smoke checks remain unverified.

Official verification requirements:
[Firebase ID token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens).
The credential-loading conclusion is based on the installed Python SDK source and
the local diagnostic, not an assumption that public certificate verification
mathematically requires a private key.

## Other security findings and release blockers

- Existing provider check accepts any nonempty firebase.sign_in_provider, rather
  than explicitly requiring google.com. Valid tokens from other enabled providers
  in this project could be accepted as Google identities. This predates this repair;
  strict provider enforcement needs a focused regression-backed follow-up.
- Existing default-app reuse accepts an already-initialized SDK app without
  checking its project against Settings. Local diagnostic confirms the intended
  project in a fresh process; multiple configurations in one process need care.
- Separate-origin Vercel/Railway CSRF restoration and third-party cookie behavior
  remain deployment blockers recorded by Phase 2B. No proxy/UI feature was added.
- Existing guest rate limiting trusts X-Forwarded-For; trusted ingress remains a
  deployment requirement. SDK verify_id_token uses its default check_revoked=False;
  application-session logout revocation is separately enforced and tested.
